# Hearth · Ember Narrative Experience Specification
> 炉心叙事体验与演化系统｜设计 / 动效 / 产品 / 编码 Agent 共用合同

- **版本**：v0.1（叙事深化提案，待视觉与产品验收）
- **制定**：2026-10-29
- **上位合同**：[根目录 NARRATIVE.md](../NARRATIVE.md)，本规范解释其实现，不取代其 Must/Should/Won't。
- **基于版本**：master@e5752ce（包含 0e958d7 炉心设定及后续完善）
- **范围**：品牌叙事、聊天主界面、生命周期/动效、项目故事、数据真实性、交互节拍与验收。
- **非范围**：把 Mock 聊天冒充真实 Agent、自动修改项目、增加后台工作台、跨设备同步炉温、未经许可地调用模型。

## 0. 核心决定：讲一个长期发生的故事，而非造一个有火焰的 Dashboard

**产品一句话**：「项目的故事还在继续，而你不必一直守着它。」

**叙事承诺**：当你走近炉边，Hearth 先接住你正在关注的事；有可靠的变化才开口；你选择下一步；离开时话题被妥善放下，下次回来能从真实的记录继续。

**核心比喻**：

- **炉心 Ember**：你与产品之间的**在场感/互动温度**，不是 Git 成绩、效率得分或健康分。
- **薪柴（项目）**：用户主动纳入关照范围的项目；每个项目有自己的故事、来源和决策历史。不是“项目越多火越大”。
- **火星（事件）**：有来源、时间、作用域的真实观察事件；不是后台线程跑动的假动画。
- **火光照见的纸页（建议）**：Agent 将事实整理为可选择的下一步；建议必须区分事实与推断。
- **余烬（可恢复的关系）**：离开后话题仍可被找回；不等于应用关掉仍在后台工作。
- **炉边/内室**：主界面只有对话；项目、证据、设置按需打开，完成后回到原话题。

反原则：不以焰高鼓励刷消息、不靠连续签到奖励留存、不将无人使用渲染成损失/失败/危险。火焰 **不是宠物养成、监控指示灯或进度条**。

## 1. 双重叙事：人的在场，项目的演进

这两条时间线独立，交叉但不混淆。

| 轴 | 它回答什么 | 可信来源 | 对用户的表达 | 绝对不能表达 |
|---|---|---|---|---|
| A / Relationship Warmth | 我与 Hearth 最近有没有互动？ | 当前会话及最近一次**成功提交**的用户交互时间 | 炉心的黯 / 温 / 旺、轻微环境反馈 | 项目正常/异常、Agent 智能程度、真实后台工作量 |
| B / Project Story | 项目自上次以来发生了什么？ | Observer 快照/事件、带证据洞察、用户记录的决定 | 对话里的「上一章 → 新变化 → 可能的下一步」 | AI 凭空推断的修改、未运行测试被判 PASS |
| C / Runtime & Consent | 当前有没有在观察/分析、能否执行？ | 真实服务可用性、分析 run 状态、授权快照 | 精确的文本状态与明确批准步骤 | 用火势或吉祥动画取代错误/权限/费用提示 |
| D / Evidence Freshness | 这份结论是何时、以什么范围得出的？ | 时间戳、HEAD、来源 ID、已消费水位 | 「截至 XX 的观察」「信息可能已过期」 | “我一直看着”“刚检查过”（实际未检查时） |

### 1.1 状态分离的视觉原则

- **火势由 A 决定**。即使项目出了问题也不能突然把火焰染成红色“警报火”；项目风险由文字/专属风险标识表达。
- **C 与 D 显式标注**。服务不可用不等于炉心熄灭；失去观察能力时应明确说“上次观察停在……”，不可仅让火变暗。
- **B 出现时才改变内容**。没有事件就不插入假的“今日 6 个项目一切正常”总结；只有确实观察了 6 个项目才可以说 6 个。
- 项目可能有很多故事，但是**屏幕同一时刻只有一个主叙事焦点**；切换项目如翻到另一章，而不是打开管理台。

## 2. 火的生命周期：从微光、点燃、长谈到余烬

> 保持根合同的三个外显档位 **黯 / 温 / 旺**。初见、点燃、复燃、静默是**过渡场景**，不再额外引入可持久的“第 4/5 档位”。

### 2.1 时间与触发规则（本地、可解释、无奖励）

| 情境 | 计算/触发 | 外显焰态 | 文案与动效 |
|---|---|---|---|
| 初次打开，确无聊天历史 | lastInteractionAt = null | 黯（未点燃微光） | 「从这里开始，聊聊你正在做的事。」炉心微弱、无历史余烬的假象 |
| 输入框获得焦点 / 开始输入 | 本地临时 UI 焦点 | 档位不变 | 炉心亮一点作为交互反馈；绝不伪称任务开始 |
| **第一条成功发送** | 服务端确认用户消息已接收 | 旺 | 一枚光点向炉心靠近 → 柔和点燃 → 对话向上展开 |
| 同一会话继续交流 | 用户有效消息成功提交 | 旺 | 小范围轻跃；连续短时间发送不无限叠加 |
| 最近成功互动在 24h 内 | now - lastInteractionAt ≤ 24h | 旺 | 稳定暖光，不重复播放点燃开场 |
| 最近互动 >24h 且 ≤7d | 24h < Δ ≤ 7d | 温 | 炉光收敛为温暖余烬 |
| 最近互动 >7d | Δ > 7d | 黯 | 炉心低亮；可以随时再次点燃，没有责备 |
| 长久后重新发送成功 | 原状态温/黯 → 成功提交 | 旺 | 复燃：先有温柔呼吸，再升到稳定焰势 |
| 发送失败 / API 超时 | 未确认落库 | **不改变持久焰态** | 输入保留、错误解释，可重试；禁用庆祝火花 |
| 路由跳转 / 刷新 | 从既有本地事实重算 | 不人为加热 | 恢复上次外显温度，无开屏闪切 |
| 暂停/退出页面 | 不必启动后台倒计时 | 时间确定性衰减 | 下次回来按真实时差决定档位，避免假后台运行 |

**边界约定**：24h/7d 用实际时间差（小时），非“昨天/上周”的模糊日历边界。用户修改系统时间时不向未来发送时间；非法/未来时间戳降级为中性“尚不明确”。本地会话时间缺失时不创造“最近回来”的文案。

**“越用越旺”的正确落地**：在 **旺** 档内部可以有轻微、封顶的动态强弱，例如最近 3 次被成功接收的用户交互带来逐步增亮，但**不新增等级、不展示分数、不奖励连续签到、不随消息数无限增长**。当用户正在阅读、思考或离开时，画面仍应宁静。

### 2.2 视觉参数建议（先形成令牌，再通过截图校准）

| 属性 | 黯 / dim | 温 / warm | 旺 / lively |
|---|---|---|---|
| 炉心轮廓 | 清晰的余烬底座、微弱内点 | 单个稳定火瓣 | 2–3 个缓慢变化的火瓣 |
| 光晕半径（设计目标） | 8–12px | 16–24px | 26–36px |
| 强调色 | 墨灰 + 淡赭 | 炭火橙半透明 | 暖橙高光，文字仍为深墨 |
| 连续运动 | 默认静止 | 极轻呼吸（可关闭） | 小幅缓动，不频闪、不循环爆裂 |
| 空间变化 | 不改变主布局 | 不改变主布局 | 不改变主布局 |
| 文字 | 从来不因焰态降低可读性 | 同左 | 同左 |

上述数值是视觉设计起点，不是必须硬编码的像素。**炉心不是整页调亮/调暗的开关**：底色、文字对比度、按钮可用性必须保持稳定。页面差异主要由局部材质、火形、光晕、问候语表达。

### 2.3 动效时间表

| Motion token | 场景 | 建议时长 | 约束 |
|---|---|---|---|
| ember.focus | 输入框聚焦、按钮 hover | 120–180ms | opacity/transform，非全页闪光 |
| ember.ignite | 首次成功开口 | 650–900ms | 一次性，成功确认后才播放 |
| ember.rekindle | 温/黯复燃 | 800–1200ms | 可中断，终态为稳定旺 |
| ember.settle | 互动结束/界面静下来 | 450–700ms | 光晕逐渐收敛，不关闭输入 |
| thread.unfold | 空态转对话态 | 320–480ms | 聊天内容在主轴展开，Composer 稳定落底 |
| note.arrive | 确有新洞察进入 | 220–320ms | 单条出现，绝不连续喷卡 |
| decision.resolve | 用户作出选择 | 180–260ms | 确认/拒绝/取消有各自明确状态 |
| ember.idle | 可选温和呼吸周期 | 5–8s | 振幅 ≤3%，省电模式/非前台暂停 |

动效禁区：大范围随机粒子、爆炸火星、滚动视差、自动播放音效、抢焦点、火焰大幅频闪、不可关闭的持续动画。不可因为高优先级洞察而以红光跳动催促用户。

**可访问性**：侦测 \`prefers-reduced-motion: reduce\` 时所有非必要动画使用静态终帧或短交叉淡化；信息从不只由颜色/火势传递；最低对比度按 WCAG 2.2 AA 逐项验收；仅键盘操作能完成核心动作；背景标签页/不可见节点暂停循环动画。

## 3. 叙事节拍：界面不是页面集合，而是一条持续的谈话

主窗口只有一个视觉主角：**对话**。默认内容宽建议 680–820px（以中文行长、宽屏实际测试为准），聊天可滚动；没有常驻左栏、右侧数据墙和“全局四宫格”。

可见导航只保留：
1. **聊天 / 项目**：轻量入口。项目入口是上下文与话题选择器，不是另起一个后台首页。
2. **头像/更多**：历史、偏好、数据源与退出等次要功能，按需弹出。移动端可以合并为一个菜单。

原有技术路由和深链接可保留，以保障证据及设置可达；但视觉上不作为默认常驻导航。证据用 inline expand / modal / 临时 sheet 展开，关闭后焦点回到原对话和当前项目。

### 3.1 六幕故事板（必须画连续图，不是六个独立 UI 风格）

#### Scene A — 初遇 / The First Ember

- 画面：中央微小炉心，短问候，宽松的输入井，**最多 2 个**预设入口；其余皆隐去。
- 用户心理：「我可以把正在做的项目告诉它。」
- 参考文案：「从这里开始。你最近在做什么项目？」
- 如果用户尚未登记项目，不能伪称“我已经观察过你的项目”。
- 第一次预设入口可为「介绍我的项目」「看看可以怎么开始」，必须真能引导登记/选择，不能直接触发模型外发。

#### Scene B — 点燃 / The First Conversation

- 第一条**确认成功**的消息触发 ignition。
- 视觉：问候和炉心轻移，第一条真实消息进入线程，Composer 自然下移。
- 用户心理：「这段关系开始了。」
- 首次失败不播放完成动效；错误本身给清晰的恢复动作。
- 当前 Chat Mock 必须紧邻会话显著标明「离线演示 · 不连接真实模型」。

#### Scene C — 围炉 / The Ongoing Dialogue

- 视觉：常规对话、稀疏的来源标签，项目上下文可切换但不铺面板。
- 用户问「最近 pindou 有什么变化？」，系统只基于权限内可读取的最新观察回答，回答里带观察时间；未获取就如实说。
- 「项目故事」可以通过一句简短的“接上回”出现，但除非有持久记录，不伪造上次对话内容。
- 细节永远可通过追问与展开获得，而不是默认展示大量指标。

#### Scene D — 轻敲 / The Gentle Nudge

- **只有真实且去重后的高价值洞察才出现**，一个可见话题最多 1 张行动小卡、最多 2 个主动作，和 NARRATIVE Must 一致。
- 结构：一句发生了什么 → 一句为什么值得注意 → 小卡（可展开来源）→「继续了解 / 稍后决定」等两个动作。
- 不在用户正在打字时弹窗抢焦点、不跳走当前会话、不因为后台有 20 个事件就发 20 张卡。
- 同一项目/同一问题重复事件合并为一个「后续更新」；其他线索放到非打扰入口。
- 若推断无足够证据，明确标“需要进一步确认”，不出现「采纳并执行」假动作。

#### Scene E — 抉择 / The Turning Point

- Agent 把可选项与风险讲清楚，用户决定是否进入操作。
- 对有副作用的操作：同线程展示**目标、范围、风险、外发内容、费用/权限（若适用）、可撤销性**，用户显式确认后才可调用已实现且获授权的执行通道。
- 根合同「确认 → 执行 → 回写」的含义是**真实受控能力**；若当前只有分析建议，则仅能确认「保存决定/启动允许的分析」，不得呈现虚假的自动修改仓库按钮。
- 失败与拒绝也是故事的一部分：「这一步没有完成。我保存了原因，接下来可以重试或换方向。」不能用胜利动画掩盖失败。

#### Scene F — 安静与复燃 / The Return

- 一段时间没来，炉温自然变温/黯，时间不是倒计时。
- 回来首先显示简短、可核验的“接上回”：
  - 有记录：「上次我们停在『是否继续分析』。这次要接着聊吗？」
  - 观察确已发生：「截至 [观测时间]，这个项目有一条新变化。」
  - 未观察：「我还没有新的观察结果。想先查看上次记录，还是重新扫描？」
- 恢复对话后播复燃，**不需看完动画才能输入**。
- **禁止**「你离开太久了」「再不回来火就灭了」「项目在等你打卡」等罪疚或施压表达。

## 4. 项目的演化：每一个项目不是一根 KPI 柱，而是一部有来源的连载

项目的“章节”不是 Git commit 的一一映射，更不能由模型虚构。建议增加**展示层的 Story Episode（故事片段）**，每个片段是一段能够追溯的上下文变化：

| 节点 | 用户理解 | 数据/行为 |
|---|---|---|
| 引子 / Introduction | 为什么关照这个项目？ | 用户给出的目标、已登记的项目名称；不读取未授权私人目录 |
| 上一章 / Previously | 上次停在哪里？ | 明确存档的对话、已记录决定或上次观察时间 |
| 变化 / Turn | 本轮真正变了什么？ | Observer 事件及其时间、HEAD/工作区/报告 |
| 判断 / Reflection | 这变化可能意味着什么？ | 确定性规则或明确标注模型推断，附来源 |
| 岔路 / Choice | 我能做哪种决定？ | 一条建议 + 有权限的下一步，不假装具备执行能力 |
| 回响 / Consequence | 决策后发生了什么？ | Run/Verifier 真实结果，或“尚未验证” |
| 留白 / Rest | 现在没必要打扰 | 暂缓、无信号、观察暂停的真实状态 |

**展示例子（仅作虚构文案样例，不是当前真实运行结果）：**

> 上次，我们为 Pindou 留下了「先验证图纸识别，再考虑全面改版」这个决定。  
> 这次我看到了一次新的提交，但还没有与你当前 HEAD 关联的测试结果。  
> 我不会把它判作成功。要先看一下这次变化，还是继续讨论界面的方向？

这段叙事把**事实 / 缺口 / 选择**接成一个故事，而不是假装 Agent 已经把全部事情做好。

### 4.1 实体与生命周期（面向将来的实现）

建议的最小展示契约（暂不强制修改后端 Schema）：

\`\`\`ts
type FlameState = "dim" | "warm" | "lively";   // 表层三态
type EpisodeKind = "change" | "insight" | "decision" | "outcome" | "rest";
type EvidenceStatus = "verified" | "candidate" | "stale" | "unknown";

interface NarrativeEpisode {
  id: string;                // 稳定可去重，通常引用已有 insight/run/event id
  projectId: string;         // 严格作用域，不得跨项目混读
  kind: EpisodeKind;
  observedAt?: string;       // 无就不写“刚刚”
  sourceRefs: string[];      // 必须能解析到受权限约束的来源
  evidenceStatus: EvidenceStatus;
  headline: string;
  oneSentenceWhy: string;
  followUpAllowed: string[]; // 由真实能力与权限决定，不让 LLM 决定可执行范围
  userDecisionId?: string;   // 仅真实持久化决定
  outcomeRunId?: string;     // 仅真实 run
}
\`\`\`

推荐事件流：ObserverSnapshot/Event → Insight（规则）→ StoryEpisode（展示层编排）→ 用户在对话中选择 → 经安全门控的分析/操作 → 写回结果。**StoryEpisode 是用户界面的叙事视图，不是新的真相来源**。

### 4.2 叙事的断章、缺口与“没变化”

- 新项目没有足够观察：说「还不了解它，我们可以先从登记和允许的观察开始」，不能凭空编年史。
- 报告缺失 = **UNKNOWN**，绝非通过。报告早于当前 HEAD 时提示 **STALE**。
- Observer 发生 gap：承认有一段时间没看到，不能推断其间发生了什么。
- 用户暂停观察：不继续说“我正在持续关注”。
- 项目删除/解绑：退出故事焦点，删除/留存按现有隐私合同；火焰叙事不能成为强留存理由。
- 有很多项目但只有一个发生重要变化：只讲那一个。其余让用户按需询问。
- 系统启动后尚未扫描：不输出全局“健康/正常”的总结。

## 5. 对话中的信息组件：只在故事需要时出现

| 组件 | 何时出现 | 默认内容 | 展开后 |
|---|---|---|---|
| EmberPresence | 空态、对话开端、回归 | 小炉心 + 一句问候 | 无需展开，不做角色养成 |
| ProjectMention | 消息涉及具体项目 | 项目名 + 最后可信观察时间 | 项目上下文切换器 |
| StoryNote | 确有关键变化 | 一句话事件摘要 + 来源入口 | 时间、HEAD/证据、已知缺口 |
| DecisionNote | 确有可选决策 | 一个建议、风险摘要、最多两个动作 | 方案依据、边界、审批字段 |
| EvidenceSheet | 用户显式要求看依据 | 不常驻，独立临时层 | 原始有权限的来源、时间、版本 |
| RunReceipt | 用户确认了真实运行 | 真实状态（待确认/进行中/完成/失败等） | Trace 和验证证据 |
| ReturnThread | 从旧话题恢复 | 上次明确记录的决策点 | 按需加载历史 |

限制：不默认显示项目卡墙、图表墙、活动流；常态主轴保持「短文案 → 对话 → 输入」；复杂对象通过单次展开/返回保持语境。所有 action label 必须是真实可执行动作，不能只是装饰。

## 6. 语言与情绪写作规范（Narrative Voice）

**人格气质**：温暖但不粘人；有判断但保留不确定性；主动但不抢方向；不把观察说成全知；不拟人化为必须陪伴、需要投喂的生命。

写作顺序（优先）：
1. **发生了什么**（带范围/时间）
2. **为什么值得你注意**（事实与推断分离）
3. **接下来你可以选什么**（通常 ≤2 个）

| 情形 | 建议文案 | 避免文案 |
|---|---|---|
| 初见 | 「从哪一个项目开始？」 | 「主人，快喂我一点火吧！」 |
| 温 | 「炉还温着。要接着聊上次的方向吗？」 | 「你已经两天没来，我好想你。」 |
| 黯（曾有历史） | 「余烬还在。我们可以从上次停下的地方继续。」 | 「你再不来，我就熄灭了。」 |
| 旺 | 「我们继续。」 | 「你的热度已达到 98 分！」 |
| 真事件 | 「截至 10:30 的观察，测试报告还未与最新提交对齐。」 | 「我彻夜监控，发现大问题！」 |
| 无事件 | 「目前没有新的、值得打断你的观察结果。」 | 「你的所有项目都很健康。」 |
| 分析前 | 「这次会把预览的内容发送给你选择的模型服务。要继续吗？」 | 「我已经帮你查了全部源码。」 |
| 失败 | 「这次没有成功。我保留了可恢复的上下文。」 | 「任务已圆满完成！」 |

产品文案不宜频繁出现“火”“炉”“余烬”。**火是视觉隐喻，语言必须像真正的产品**：除初遇、回访、故事章节等少数场景以外，日常尽量正常说话，避免每条消息都强行拟诗。

## 7. 视觉与材质：温柔的火，不是一座 3D 壁炉

### 7.1 视觉锚点

- **品牌符号**：由 1 枚独立的 EmberGlyph 构成。休眠时像余烬核，点燃后形成一小簇抽象火瓣；不能直接照搬 Hark 的天空/云层/玻璃柱。
- **排版**：编辑式短标题 + 舒适的中文正文。衬线标题仅用于问候/章首，不要让每条聊天都用超大衬线。
- **色彩**：延续已有暖纸、墨色与炭火橙令牌，火势影响局部光影不改变语义色。
- **材质**：“玻璃井”只表示输入的精致层次（边框/背景对比），不是大面积磨砂玻璃和模糊背景。
- **留白**：中心输入和当前对话具有最大的视觉权重；历史、证据、控制入口都靠后。
- **暗色主题**：应是合理、可读的夜色墨绿/炭灰版本，不简单整屏变黑或模拟一间暗屋。

### 7.2 必须避免的“同质化回退”

- 不把首页做成「4 个项目统计 + 8 张卡 + 3 个图表」。
- 不把聊天框镶在一个信息密集的左右三栏工作台里。
- 不做满屏山峦、瀑布、自然环境照片作为背景。
- 不持续有烟、火星或漂浮气泡造成视觉噪声。
- 不设计三个只换配色的“候选 UI”；必须围绕同一故事连续展示三个时间场景。

### 7.3 设计令牌（新增命名建议）

设计 Agent 输出独立的 Ember motion / appearance token，再映射到现有 \`apps/web/src/styles/tokens.css\`，避免各页面散落硬编码：

\`\`\`css
/* 建议 token，尚非已实现样式 */
--ember-glow-dim: 0.10;
--ember-glow-warm: 0.30;
--ember-glow-lively: 0.55;
--ember-ignite-duration: 800ms;
--ember-rekindle-duration: 1000ms;
--ember-settle-duration: 600ms;
--thread-unfold-duration: 400ms;
\`\`\`

实际实现只在根容器挂 \`data-flame-state="dim|warm|lively"\`，单点控制视觉。**不把本地互动次数上传、不用 Analytics SDK 才能变焰**。

## 8. 能力与诚实边界（必须和真实仓库一致）

截至本规范读取的 master 基线：

- Observer 能读取登记项目 Git 状态及显式声明的 JUnit 报告，**不运行测试、不读取完整代码进行审计**。
- 后台确定性洞察可从事实流消费并生成规则洞察；不是通用自主规划 Agent。
- Pi 项目分析需用户预览上下文并主动批准，远端模型可能有费用；不能由 UI 重启/打开页面暗中触发。
- 当前 \`/chat\` 路由仍是**Mock Adapter 的对话演示**，不是已实现的统一真实 Agent 会话；首屏文案不能暗示全功能已上线。
- 现有后端已分离本地/演示数据，UI 必须标注当前 mode；演示例子不能掺入真实项目。
- 对执行/审批的叙事必须检查当前后端能力。UI 不能新造“批准执行→自动改仓库”的通道。

**里程碑分层**：

- **L0：叙事外壳可交付**：根据本地真实聊天时间与 Mock 演示实现炉温、初见/点燃/复燃、简洁对话主界面，所有演示声明清晰。
- **L1：真实故事卡**：只接已有 Observer + Insight 的只读事实，转成一个可展开的 StoryNote；不调用 Pi，不执行操作。
- **L2：用户主动深读**：既有 Pi consent/preview/run 进入同线程展示，正确回写分析结果；需要真实跨页面上下文桥接，不是仅复制 Markdown。
- **L3：长期 Agent**：跨会话的项目决策连续性、验证过的自主步骤与可恢复运行；须先新增持久化与安全合同，**不在本次交付范围**。

## 9. 编码 Agent 实施顺序与文件边界

### Gate N0 — 设计锁定（不先改全部页面）
1. 交付一张 **Narrative Arc Map**：初见 → 点燃 → 长谈 → 轻敲 → 决策 → 复燃。
2. 交付三张**连续故事**高保真图（同一人、同一项目、同一产品，非三种颜色风格），包括初次打开、发生变化、离开后回归。
3. 提供 3 个焰态的动画静态关键帧和 1 个不超过 15s 的真实浏览器 motion capture。
4. 明确来源/状态/授权信息在 UI 何处呈现。经人审后才进入 N1。

### Gate N1 — 炉温与纯对话骨架
- 新建 \`EmberPresence\`, \`FlameStateResolver\`, \`NarrativeShell\`, \`NarrativeComposer\` 等可测试单元。
- 将主入口重排为 Chat-first，隐藏常驻 NavRail/占位 Drawer；不删原有可达的项目/洞察/设置路由。
- 优先使用后端已有聊天历史的确认时间；仅会话临时互动状态可本地缓存。持久化字段不在这一步大改。
- 页面从空态切换到线程不得丢失输入、焦点或乐观消息；服务端确认前的火焰仅做焦点反馈。
- 修正/验证聊天消息呈现顺序：**用户消息成功后仍在历史中**；失败后能恢复草稿。不把只收到 assistant 回复误判为用户消息已成功持久化。
- Mock 模式显著标明；暂停/断网/报错不混同于黯态。
- Gate：单元 + Chromium E2E + reduced motion + 390px 移动端截图。

### Gate N2 — 项目故事与轻敲
- 加入 \`StoryEpisodeAssembler\`：只读组合已授权的项目事实、洞察、来源引用；先不动观察器采集与规则合同。
- 生成短版 StoryNote，列表不超过一张主卡、两个动作；其余不打断，允许用户主动追问/展开。
- 严格过滤跨 project/epoch 不匹配的 insight、缺口或过期来源，错误保持可见。
- 在同线程显示「发生了什么 / 为什么 / 你要不要继续看」，点开证据能返回原焦点。
- Gate：真实 fixture E2E 至少覆盖零事件、一项事件、重复事件、STALE/UNKNOWN/GAP、项目切换、来源越权。

### Gate N3 — 决策的连贯闭环（先非破坏性）
- 把 Pi 的 **预览 → 确认 → 运行 → 输出**放入同一条对话，不隐含自动调用模型。
- 让已完成/失败/取消的真实运行结果能够回到当前线程；复载后不丢运行状态。
- 将“记下决定”与“执行操作”区分，用户批准的是实际可用的能力，不允许虚构完成。
- Gate：模拟失败与取消、重启恢复、二次确认、旧同意不可复用、来源变更需重新同意，全部保持原合同安全约束。

## 11. 风险、冲突与后续决议

1. **文档缺口**：根 \`NARRATIVE.md\` 引用了 \`docs/STYLE-BIBLE-v6-EMBER-SEED-2026-10-29.md\` 和 \`handoff/qa/acceptance-checklist-v6-2026-10-29.md\`；读取 master@e5752ce 时均未找到。实现 Agent 不得假定已有这些文件；先补齐或以本规范作为 **提案验收依据**，根 Must 优先。
2. **老 UX 合同冲突**：\`docs/02-UX.md\` 的常驻左栏与右侧 Drawer 是历史基线；新的用户批准方向是 Chat-first。迁移时保留已有业务/安全功能和深链接，但主表面遵守 \`NARRATIVE.md\`，冲突项须明确登记 ADR。
3. **时间 vs 使用惩罚**：火温是审美上的关系隐喻，不能优化出连续使用压力；提供关闭呼吸动效/简化焰效的选项。
4. **故事 vs 事实**：文案可以有情绪，但决策必须可追溯；模型结论是候选判断，不是观察事实。
5. **品牌 vs 成本**：优先用轻量 SVG + CSS 表现火形，非必要不引入 3D 引擎、视频背景或大型 shader；先证明性能与无障碍，再决定是否增加高级特效。
6. **数据保留**：离开后还在的是本地**已有记录**，并非产品在后台自动继续理解一切。用户可以暂停观察、删除记录与控制模型外发。

## 12. 给设计与编码 Agent 的简短交付指令

> 在动任何 UI 代码前，完整阅读 \`NARRATIVE.md\` 与本规范。将 Hearth 设计成“用户回到一座可以继续对话的炉边”，而不是“带火焰动画的项目工作台”。先交付初遇、轻敲、回访三张连续高保真真实浏览器原型及 3 态动效；确认后实现聊天主表面。不得伪造 Agent 活动、项目健康、已完成行动；必须保留对话之外的证据可达性、真实授权与错误状态。每一阶段附截图、录屏、测试和已知未实现能力表。

**成功时用户应该能说出**：「这次回来，它还知道我们上次停在哪里。它只告诉我值得决定的事，其他的我想了解再问。火光让我感到有温度，但不会催我使用。」

## 13. 首次进入与初始化动效（2026-10-30 用户修订）

用户明确要求补足注册、开屏与页面过渡，并指出现有圆形叠加火焰不具备应有的精细程度。本节为本次实现依据，替代“直接出现空聊天页”的开场。

| 节拍 | 用户看见与行动 | 动效编排 | 完成依据 |
| --- | --- | --- | --- |
| 初光 | 炭心、Hearth 字标、短邀请；开始/跳过 | 轮廓 500ms 显现，光晕 900ms 收拢；无强制等待 | 仅视觉呈现 |
| 相识 | 可选称呼、本地保存和离线演示说明；进入炉边/返回 | 文字与字段 280ms 依次展开；持续共享炉心，不切不同模板 | 本机偏好写入；失败说明且允许临时进入 |
| 入席 | 欢迎退场、火焰沿主轴收缩、输入井展开 | 700–1000ms；输入不受转场阻塞，结束聚焦 textarea | 欢迎完成与聊天成功严格独立 |
| 开口 | 用户成功消息进入真实历史 | 800ms 点燃，炉芯先亮、外焰生长、尖端稍后跟随 | API 成功并回读用户消息 |
| 回访 | 直接恢复对话，无重复初始化 | 250–450ms 轻入场；不重播点燃 | 真实消息时间推导焰态 |

本阶段不新建账号系统、不新增后端授权或项目访问范围。浏览器内欢迎完成标识与称呼是 UI 偏好，不能用于炉温、登录态或执行授权。欢迎必须支持键盘、跳过、重看与桌面 1440×900 / 1280×800；减少动态效果/手动暂停/隐藏页面均有静态可读版本。

组件交付：独立可复用的 `EmberPresence`（SVG 连续火形与受控运动）和欢迎流程，配套精细排版、表面、按钮、输入与聊天过渡。验收覆盖初见、填写、跳过、二次进入、失败草稿、首次成功与三态关键帧，保存真实截图和短录屏。

本次验收以桌面端为准，用户明确说明设计不涉及手机；此前矩阵中的移动端项不纳入这次精修范围。

### 13.1 GSAP 编排（用户明确指定技能）

动效实现采用本地 `gsap-core` / `gsap-react` / `gsap-timeline` 指南：入场和退场由带标签的 Timeline 编排；炉芯→侧焰→外焰错时点燃；对话输入井保持同一个 DOM 节点，按位置差做 transform 过渡。持续运动以局部、封顶的形变和轻呼吸表现；不用滚动视差、爆炸粒子或随机噪声充当叙事。

所有时间线有组件作用域与卸载清理；前后台切换及暂停恢复保持播放位置；减少动态效果直接到稳定可读帧。开场不阻塞跳过和输入，初始化成功与真实聊天成功是独立状态。

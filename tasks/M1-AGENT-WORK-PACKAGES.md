## 角色和协作方式

- **核心（难）**：主 Agent/高能力 LLM 负责需求裁决、权限/路径、项目身份、合同及 SQLite migration、来源真实性边界、观点修订和最终集成审查；不得把这些职责交给只负责样板的 Agent 独立拍板。
- **辅助（简单）**：外部 LLM 按明确文件范围实现合成数据、非安全敏感测试、UI 展示组件或验收文档。它的交付是待审查代码；主 Agent 检查实际 diff、运行测试、验证边界后才可标完成。
- 最多两个子 Agent 并行，文件独占；涉及合同和数据库迁移的改动串行。多个独立 LLM 如不能共享即时工作区，分别基于同一提交交付 diff，并按依赖串行合入；不要同时改同一文件或生成互相覆盖的提交。
- 细分任务以 `tasks/m1-work-items.json` 为唯一技术状态源，记录 ID、负责人、状态、依赖、证据和可选外部任务引用；`DEVELOPMENT-PROGRESS.md` 是同步的人工可读摘要。看板、结构化清单、`manifest.json`、`handoff/`、依赖锁文件及 CI 由主 Agent 集中维护；辅助 Agent 不得自行标记 Gate 通过。每项完成后立即更新状态源并在看板打 `[x]`，注明命令、平台、证据和未完成风险。外部 GitHub Projects/Notion 可以后按 `external_ref` 映射，不作为第二状态源；当前未创建或同步任何外部看板。
- 辅助模型只接接口已冻结、输入输出明确且可自动验证的工作；连续修复最多三次仍未通过时停止，在 `handoff/BLOCKERS.md` 留证与恢复命令，交回主 Agent，不反复绕过失败测试。
- 以下新增路径是**预留所有权**，并非声称文件已经存在。必须修改已有共享文件时先交由主 Agent 串行处理。每项开发前检查当前接口；不能满足上游合同就记录阻塞，不自行绕过。
- `manifest.json` 中 M1-A～D 的依赖表示阶段完成顺序，细分任务的实际调度依赖以 `m1-work-items.json` 为准；因此 D-C0/D-S0 可在 M1-C 完成前启动，但不得将 M1-D 标为完成。

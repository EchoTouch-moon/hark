# Hearth · 后台项目理解与重新发现

2026-10-30 · 用户工作场景补充。本文记录目标产品与建议设计，**不是当前已实现功能或真实目录读取授权**。安全、隐私和既有权限合同继续生效。

## 1. 产品定义与用户原话的含义

Hearth 是安装在电脑上、在用户授权范围内持续工作的个人项目助手：自动认识散落的旧项目，为每个项目保留独立记忆；在设备空闲、许可与预算允许时研究相关领域和现成实现；帮助用户重新理解项目，判断值得继续、适合借用已有方案、需要保留观察或可以考虑归档，并通过随时可用的对话继续探讨。

用户背景：Vibe Coding 降低了做雏形的成本，电脑里积累了许多新旧小项目和大项目。用户可能已经忘记某个项目做什么、做到哪里、为何搁置；有价值的创意也可能被遗忘。目标收益是重新掌握与选择自己的项目，而非仅知道Git/测试状态。

本轮明确的核心：

- 一次添加若干授权目录，自动发现其中的项目，减少逐个手工登记。
- 项目可能年代不同、材料不同，不将目标产品限定为Git仓库。
- 按项目建立、更新和检索记忆，支持“这个项目当时是什么、做到了哪、还能怎么接着做”。
- 用户可随时聊天，既能讨论一个项目，也能询问整个已授权项目集合。
- 后台可以自行选择一个项目开展有界分析与外部研究；不以用户先发问或先补全旧目标为前提。
- 得到值得关注的结果后，能通过应用内卡片或获准的本机通知邀请用户回来讨论。
- 电脑忙时让出资源，空闲时继续；关闭前台窗口不应自动终止已启用的后台服务。
- 火焰/炉心作为可调整的表达，服务项目交互，不决定产品组织方式。

## 2. 对上一版需求的修正

| 上一版偏重 | 本轮目标 |
|---|---|
| 用户逐个登记Git项目后进入绑定线程 | 用户授权目录，系统自动识别项目；模糊边界再让用户轻量校正 |
| 先选择一个项目，再开始所有对话 | 有授权项目后，可以直接全局问项目取舍，再深入一个项目 |
| 需要用户先说明目标才开始有意义的工作 | 先从已有材料重建概况，推测目标明确标为待确认；必要时才补问 |
| 当前问题与决定是主要前台组织 | 保留该组织，同时补齐后台持续理解、主动重新发现与全局项目盘点 |
| 多项目浏览和项目记忆可稍后增强 | 多项目身份与独立记忆是基本结构，不再推迟成视觉增强 |
| 主动呈现主要在打开页面时 | 页面内发现 + 可独立于窗口工作的本机通知入口 |
| 火影带动页面叙事 | 项目从被遗忘到重新掌握、再到用户选择下一步，构成主故事 |

## 3. 用户旅程

### 安装与一次性设置

安装并启用本机后台服务；选择允许只读了解的目录，能排除目录和文件类型。分别说明分析采用本地模型还是已配置远端模型、允许发送哪些内容、公开研究范围/预算，以及本机通知偏好。后续在这些已持久化的许可内运行，不逐个项目反复要求相同确认。

目录只读许可不会隐含远端外发许可。公开检索只使用允许的公开问题表述；私有源码、绝对路径和凭据不进入搜索词。既有Pi手动分析仍保留原有逐次预览，本轮不把该接口改为自动调用；后台分析需独立、可撤销、逐次出站复核的持久政策。

### 初次盘点

先进行轻量项目识别，逐步建立各项目的简短概况，再按资源和预算安排深入了解。无需等全部目录分析完成才能使用；已认识的项目可以先谈，尚未覆盖的部分明确显示。

文件夹名称不等于项目身份；一个目录可能含多个项目，一个项目也可能有多个材料目录。识别不确定时展示候选边界，由用户合并/拆分/排除，不擅自移动文件。不跟随越过授权边界的符号链接；跳过依赖缓存、构建产物及无关大文件。Git是有用线索，非Git项目也属于目标范围。

### 安静工作

在资源允许时选一个项目继续分析，找回它的用途、已有成果、未完成线索与相关领域，研究是否出现新的可参考方案。保存检查点，让同一工作可中断、恢复和增量更新，避免每次都重读整个目录或重复调用模型。

### 值得回来时邀请

发现有价值的变化，先保存可追溯判断，再按用户通知政策呈现。通知说明“哪个项目、发现了什么、为什么值得看”，打开后直接进入该项目和该判断的讨论。单纯项目放置很久不构成提醒理由；没有新价值时保持安静。

### 用户随时主动盘点

用户可以问“有哪些值得重新拾起的想法”“哪些项目已有成熟替代”“哪些适合先归档”。全局对话先检索已授权项目的概况、研究与判断，说明覆盖范围及缺口；深入时只调取相应项目的材料。不能为了回答全局问题临时扫描未授权目录。

## 4. 项目记忆：分层、带出处、按需取回

“非常庞大的上下文”应通过持久记录与检索管理，而不是把每个项目的全部材料长期塞进一次模型请求。建议分层：

| 层 | 内容 | 使用方式 |
|---|---|---|
| 项目概况 | 做什么、可能的原始意图、技术和入口、已有部分、尚待确认的地方 | 全局盘点与选择项目时读取 |
| 项目证据索引 | 文件、文档、观察记录、相关片段与版本/时间 | 针对问题取回，变化后增量更新 |
| 用户记忆 | 已确认目标、补充背景、约束、选择及搁置理由 | 优先于模型猜测，允许用户修订 |
| 研究记录 | 外部来源、获取日期、适用条件、比较与局限 | 评估是否需要新一轮研究 |
| 判断与修订 | 当前观点、支持/反面证据、用户反馈、为何改变判断 | 主动建议与回访连续性 |

这些是设计概念，具体存储方案待ADR。每条内容绑定项目与来源；模型推测不能自动成为用户当年的真实动机。旧对话全文作为可查记录，不能替代结构化概况和决定。全局检索可以连接授权内多个项目，但不无边界混入各项目的原始内容。

记忆应知道自己的边界：未读文件、没有保存的历史、缺失源或失效研究均可表达“不知道”。撤销目录许可后，相应内容与衍生记忆的后续使用按明确保留/撤销规则处理，不能凭缓存绕开许可。归档项目不等于删除文件或清除全部记忆。

## 5. 外部研究与项目取舍

研究应围绕项目实际想解决的问题，而不是只根据项目名称搜索。比较至少考虑适用目标、已有实现、差异、可复用方案及恢复开发的障碍；具体资料存在性与结论需真实获取与核验，不预编市场信息。

建议结果可以是：

- 值得重启：说明有何价值、哪些部分值得保留、先验证什么。
- 值得调整：原问题仍有意义，某些实现可以采用现成方案。
- 保留观察：资料或价值依据不足，先不占用注意力。
- 归档候选：说明理由和可能的反例，供用户决定。
- 暂不能判断：缺少目标、材料或可靠外部证据。

“别人已经做得很好”是比较证据，不直接推出“用户没有继续的必要”。学习、个人使用、隐私/离线要求、独特工作流和商业目标可能产生不同选择。目标不明时，先给条件化建议，或在真正影响选择时提一个具体问题。

判断需要区分：本地观察事实、外部来源事实、推断、建议和用户决定。研究不能证明创意在全球唯一，也不能保证搜索到了所有替代品。记录查过什么和未覆盖什么，允许用户反驳与后续修订。

## 6. 空闲调度与资源让路

目标为本机后台服务与按需交互窗口分离。现有网页/服务进程不是已完成的安装与常驻方案，具体macOS集成、启动及打包方式仍需技术选型。

建议后台链：项目发现 → 初步概况 → 研究候选 → 深入取证 → 受限外部研究 → 形成判断 → 持久记录 → 评估是否提醒。

- 后台逐个项目推进，不把大量项目一次性送给模型；交互请求优先。
- 资源忙、用户暂停或预算不足时停止启动新重任务；已开始工作可中断、记检查点并恢复。对在途网络调用诚实记录，不能声称能撤回已经外发的内容或费用。
- 空闲判断基于允许采集的系统资源信号和明确政策，不读取键盘内容或屏幕来推断用户工作。
- 资源阈值、持续时间、频次、并发和电源政策待实测，不预设“CPU低于某值”就等于用户有空。
- “唤醒”在本方案中指电脑已运行且资源允许时恢复后台任务；从系统睡眠唤醒硬件尚未确定，不作为默认能力。
- 外部资料没有变化、项目没有新证据且未到授权的再审周期时，不持续消耗模型调用。新外部资料可以在本地项目无变动时带来重新评估机会。

## 7. 通知和对话

本机通知为目标核心入口之一。实际发出前需有系统许可、用户通知偏好、已保存且来源有效的判断，并服从去重、冷却和安静时段。系统不支持或用户拒绝通知时，应用内发现仍可用。

邀请句可以自然，但应带实质内容，例如（文案示例，非真实研究）：

> 我重新看了你之前的X项目，找到一种可能降低后续实现成本的参考方案。要一起看看适不适用吗？

主动作打开相应讨论，次动作稍后看；搁置与不再关注要真正影响后续策略。锁屏内容展示范围可配置，不把私有项目细节默认当作公开通知文本。

进入对话后先恢复项目简况、当前判断与来源，再让用户追问。全局对话与项目对话都需要，但应明确当前讨论范围；“继续这个项目”不能悄悄变成代码执行。

## 8. 项目处理的边界

后台可以在许可内写Hearth自己的索引、概况、研究和候选判断。推进、借用方案、归档和删除建议均可由它提出。

“在Hearth里标记已归档”“移动项目文件”“删除项目文件”是三种不同操作。前者仍需可理解的用户选择；后两者不属于自动研究许可，必须独立展示具体对象与影响，并遵循真实行动政策。当前不自动归档、移动或删除任何用户目录，也不因为模型认为无价值而做这些操作。

## 9. 核心与后续

当前目标核心：目录授权与发现、多项目独立记忆、找回旧项目、随时全局/项目对话、有界后台研究、资源让路、有证据的取舍建议、低打扰发现与本机通知、用户决定和回访。

增强候选：更丰富的目录整理、项目关系图、记忆可视化、批量导出。未来方向：自动开发/实验、实际批量搬迁或删除、多端与多人协作；这些不因“放着不管”自动获得授权。

最小验证应覆盖一个授权目录内多个新旧项目：自动认识、分别记忆、找回旧意图并标注猜测、取得真实参考、主动提出一个有用建议、点开继续讨论、全局问一次项目取舍；期间负载上升可暂停恢复，无未授权写入与外发。技术阈值和样本规模待修订实施计划，不把本文标为工程PASS。

## 10. 当前工程差距与下一步

可复用：既有只读Observer、规则Insight、持久线程、最小项目绑定、人工Analysis的内容确认和来源边界。

需建设/验证：目录级安全发现、非Git材料理解、项目概况与长期记忆、跨项目检索、资源感知调度、独立后台研究许可、真实对话、可修订判断、原生本机通知与安装/常驻生命周期。

这次补充将多项目、记忆与后台生命周期提升为核心，扩展了旧G0覆盖的产品场景。下一步应先更新差距、依赖和验收映射，再分阶段实现；保留已有M0/M1与安全门禁，不把继续做网页等同于完成这个产品。

本轮仅记录和校正需求，没有开始扫描真实目录、安装后台服务、运行研究、读取凭据或发送通知。

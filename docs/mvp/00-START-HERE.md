## 一句话

**Hearth 是一个本地优先、长期理解项目的智能同行者：它在用户预先许可的范围内持续观察和研究，形成可反驳、可修正的项目观点，主动提出有证据的计划；真正执行工作必须在用户审阅具体方案并明确发起之后。**

产品主张：**让项目的生命，被看见、被理解、被延续。**

## 真正的 MVP 闭环

> 已登记且获授权的项目 → 可信观察 → 挑选一个值得研究的问题 → 许可范围内的公开资料检索 → 有引用的独立观点和建议计划 → 安静、适时呈现 → 用户采纳/修改/搁置/反驳 → 持久记录并在新证据出现时修订观点。

MVP 必须至少用**一个真实本地仓库 + 可控外部研究证据**完整走通以上闭环；不能只用 Mock 画面替代。未获得模型/外部检索配置时允许以“受阻/未配置”结束，并用固定 fixture 验证同一状态机，但不得标注真实闭环 PASS。

## 关键产品决定（本轮已达成共识）

- 火焰是**项目生命的视觉投影**，不是积分、健康度、生产力或已完成比例；不靠点击、聊天次数直接判定项目完成或成长。
- 取消“添柴”“添柴扫描”“火势活力百分比”及维持火势的行为暗示；真实手动扫描动作直称「立即检查」。
- **一座主炉心，多段项目故事**。项目与对话线程不是同一对象；无可信绑定不得跨项目借用证据或焰态。
- Hearth 可以在**预先设定的观察范围、研究权限、预算和外发规则内**自主寻找 GitHub、论文、技术文档，形成观点并主动反馈。
- Hearth **不能**因“已获低风险权限”“已制定计划”而自动修改代码、运行项目实验、提交 PR、发邮件或增删日历；这些真实行动需要展示具体方案、由用户明确发起并授权其范围。
- 观点不是聊天临时文案：必须拥有证据、可证伪条件、历史版本、用户反馈和后续结果。
- 默认安静。没有新价值时不推送；后台运行与 UI 火焰运动是两回事；断线或缺失来源必须展示真实可观测边界。

## 和当前仓库的关系

- 现有 `master`：已有 Observer / Insight / 受控 Pi Analysis 等工程能力；README 将“主动研究/通知/项目观点”列为尚未实现。
- [PR #5](https://github.com/EchoTouch-moon/hark/pull/5)（`codex/ember-narrative-motion`，基线 `fe5464e`）：对话优先的桌面 UI、欢迎、玻璃后火影、GSAP 和五态视觉资源，**是设计资产，不代表心智闭环已实现**。
- PR #5 旧版 `NARRATIVE.md`、`docs/EMBER-STORY-SYSTEM.md`、`projectEmber.ts` 里仍有“按对话数升火”“全部建议卡完成即金火”等与本轮方向冲突的规则。新 MVP **以本目录产品意图为准重新裁定**；既有安全、隐私、访问授权、证据合同始终优先。
- 新 Agent 必须先盘点原有实现并列出复用/淘汰/迁移表。不可把“代码存在”当成“已通过端到端验收”。
- 仓库历史文档和证据不删除；本目录是新的 MVP 产品说明和实施入口。**本文不是合并授权**：代码工作走独立分支/PR，经评审后再合并。

## 与 Hark 的关系

Hark 是启发来源：持续对话、主动提供有用见解和低打扰体验。Hearth 的可区分核心是**本地项目生命、可信证据、可修正的项目观点、研究先行、行动后置的用户主权**。不仿造 Hark 的界面、品牌、资源和未验证能力。

## 实施纪律

- 优先复用已有 TypeScript monorepo / Node / React / SQLite；不要求 Docker，也不默认增加重型 Agent 框架。
- 默认离线安全启动。外部研究与模型需要单独显式配置，受限、可审计、可停止。
- 任何真实外发均须满足来源、敏感信息、费用与授权边界；禁止将私有源码、路径、密钥、长日志直接放入搜索词。
- 用真实可追溯事件驱动 Narrative Engine，再由 Flame / Story 分别投影；不能让动画反向驱动业务事实。

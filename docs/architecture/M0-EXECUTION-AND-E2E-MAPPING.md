# M0 合同裁决：审批绑定与旧 E2E 适用范围

状态：本地合同映射，**未实现审批执行链，也不是 Gate PASS**。优先级仍是项目理解、来源、观点、反馈和修订；下列执行要求用于保持现有安全底线，不构成开发真实执行器的授权。

## 审批绑定：保守合同

针对 `docs/04-CONTRACTS.md` 中路径以 run 为单位、`ApprovalGrant` 以 card 为单位的差异，后续实现应在可信持久状态中验证以下链条：

1. 请求主体由经认证的服务端上下文提供；run 必须存在，并通过持久关系指向同一 card 和 action。card、candidate、action、项目和目标的真实归属均由服务端核验，不信任客户端提交的 projectId、risk 或 status。
2. grant 的主体、card、风险下限、能力、动作摘要、目标摘要和有效期必须覆盖当前具体动作；其一次性消费状态须在事务中检查与预留。`L3` 永不允许，`L2` 必须具有在线明确授权；研究或保存计划的许可不能替代执行许可。
3. 从服务端静态注册表确定动作的风险下限、效果、可用能力、严格参数及目标范围；注册表规则尚未冻结的动作保持关闭。不能根据动作名称或客户端的 risk/effect 推断许可。
4. 实际外部副作用前再次读取并核验 grant、目标/动作摘要、当前 scope、有效期、消费状态和来源版本；超期、撤权、篡改、来源未知或过期均失败关闭。
5. 外部操作的成功与本地完成记录无法组成单一原子事务；如结果不确定，进入 `pending_verification` 并独立回读，不自动重试可能已发生的副作用，不由模型自报完成。

当前 `runs.card_id`、`runs.action_id` 和 `approvals.card_id` 仅提供部分关联字段，不能单凭它们证明上述链条已成立；身份认证、注册表、批准消费、来源复核、独立 verifier 和外部执行均未接通。后续实现需附跨项目、篡改、过期、撤权、并发占用及崩溃窗口测试。

更新（2026-11-03）：上述第 2–4 条的部分校验已有**纯预检**实现，见 `M0-ACTION-POLICY-GATE.md` 与 `src/action-policy.ts`。它固定校验顺序并按动作类型冻结参数、风险下限、效果、能力与成本上限，但未读写持久层、未占用 grant、未认证身份，也仍然没有执行器；因此本条目的"未接通"结论不变。

## 版本与真实来源

旧 `SourceRef.sourceType` 没有普通本地项目专用类型；`EvidenceRef` 的 observer 类型只描述引用结构。未来正式目录来源需引入明确版本的本地 source 合同，绑定可信授权根、项目 ID、来源 ID、epoch、范围和状态，提供兼容及迁移测试；不得把 `fixture` 或受禁 vault 冒充已授权本地项目。当前不定义或开放真实读取 API。

Event 的旧结构仍允许 `expiresAt` 缺失以兼容读取；作为当前观察事实的时效预检缺期限即 withheld，通过时仍需可信授权与来源核验。详细裁决见 `M0-CONTRACT-REVIEW.md`。现有 M0 结构/合成测试不能替代用户身份、源内容真实性或 Windows/远端检查。

# M0-A 项目理解合同（首版，待完整审查）

本合同围绕项目理解、来源、观点、用户反馈及后续修订。结构由 `src/domain-contracts.ts` 定义，`OpinionBundle.contractVersion` 为 `"1"`；修改已有版本的含义或字段属于破坏性变更，需新增版本及迁移/兼容测试。旧 Action/Run 合同继续保留在受控执行层，不是当前开发中心。

`OpinionBundle` v1 的反馈数组仍只接受 v1；`FeedbackV2` 是独立版本的反馈记录，fixture 存储按其显式版本读写。未来若要在单一 bundle 中返回 v2，须定义新的 bundle 合同，不更改 v1 的含义。

## 结构与语义

- `Project` 为持久项目身份。名字或目录不是身份；`GoalRevision` 是用户的目标记录，不假定系统已知目标。未发现描述时可为空。
- `EvidenceRef` 区分观察事件、公开研究来源、用户决定三种引用。只有观察引用有 epoch；公开研究与用户决定不能伪装成对用户项目的直接观察。
- `GroundedFact` 把陈述与引用及其主题类型绑定；它的名称和合法结构**不证明陈述被来源支持**。推断另列在 `OpinionRevision.inferences`。候选观点仍需可信数据层核验及人工价值评审。
- `Opinion` 表示项目内一个话题及当前版本号；`OpinionRevision` 把事实陈述、推断、反证、限制、看法、备选和可改变判断的条件分开。没有反证时必须说明缺口。
- `ProposedPlan` 与版本相连，固定 `executable: false`。`Feedback` v1 记录用户采纳、修改、搁置或反驳；显式 `contractVersion: "2"` 的 `FeedbackV2` 增加独立的拒绝。反驳须有理由，搁置须有恢复时间；用户不采纳或拒绝不等于事实被证伪，也不自动覆盖观点。
- `OpinionBundle` 检查提供的项目、观点、版本、计划、反馈及其中证据的项目与身份引用一致。`RevisionPair` 检查同一项目和观点的相邻版本编号及不同版本 ID；原因单独记录。

## 已覆盖的边界

Zod 严格对象拒绝未知字段；字符串和集合有界。禁止外部研究引用冒充项目观察；拒绝不一致的项目、观点、计划、反馈引用，拒绝可执行的计划和不连续的版本对。旧 `Candidate` 和 `ActionCard` 也拒绝引用其他项目的 Action。合成数据与断言见 `tests/domain-contracts.test.ts`、`tests/contracts-state.test.ts`。

上述仅为**自包含记录的结构和交叉一致性**：传入的 ID、来源质量、授权状态和内容仍可伪造，不能作为公开展示或访问文件的凭据；关联的 candidate 与 card 属于不同对象，也须由未来的持久化层检查其真实归属。

## 必须在展示或实际使用前完成

1. 从可信存储而非输入中确定项目及调用者 scope；重新核验来源存在、授权及可访问性。观察流须核对真实当前 epoch，研究须核对来源、权限及可用性，用户决定须核对真实版本与撤销状态。
2. 缺失、越权、旧 epoch、撤权、暂停、过期或撤回的引用应 withheld 或标记失效；保留历史，不可凭旧快照的 `observed`、`available` 或 `active` 自证有效。项目已删除或删除中不得继续展示为当前可用观点。
3. 证明陈述确实得到其来源支持，并人工评估观点质量；结构校验不能把模型输出升级为权威事实。具体的来源定位、版本、URL 与保留规则仍须在数据层契约中完成。
4. 数据库以项目绑定的外键、唯一约束及事务保证版本和反馈隔离；观点版本只追加，使用 `expectedRevision` CAS 防止并发覆盖，并测试重启与事务回滚。
5. 用户修改内容和新目标需由目标/决定版本记录；反馈本身不等同于修订内容。恢复、撤权后的缓存使用及保留策略须单独实现和验证。

首轮合同实现时未新增数据库迁移或持久化；此后已增加仅供合成数据使用的观察、用户决定和观点版本存储，见 `M0-B-FIXTURE-CHRONICLE.md` 与 `M0-C-FIXTURE-OPINION-MEMORY.md`。实际来源核验、目录扫描、模型、网络、通知和执行仍未开启。M0-A 全部合同复核与 M0 Gate 尚未完成。

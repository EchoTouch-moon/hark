## 0. 裁决概览

**核心发现：Hearth 与这篇文章不是"相似"，而是同一个第一性原理的两次推导。**

原文的第一性原理是：*"单任务的上限取决于模型能力，多任务的上限取决于人的注意力"*，因此 *"Session 应当是系统的实现细节，而不应是用户的认知负担"*。
Hearth 的第一性原理是：*"你来，火就旺；你走，火就黯；有事它轻敲一下，没事它安静陪着"*。

两句说的是同一件事：**系统要为人的注意力负责，而不是把系统的复杂度转嫁给人的认知**。这就是为什么会觉得"底层有很大相似之处"——不是模块像，是命题相同。

**但两者完成度不同，且方向相反：**

| | DeepSeek | Hearth |
|---|---|---|
| 把"克制"做成了什么 | **可测量的机制**（准入表 / observe 默认 / 投机执行 / 100 词硬限 / 打扰门槛） | **可感知的体验**（≤1 卡 ≤2 chip / 不刷屏 / 焰态） |
| 把"自主"做成了什么 | 激进（Worker 以 OS 用户无审批执行、Watchdog 可改提示词） | 保守（逐案确认、执行默认禁止） |
| 弱在哪 | 授权层（原文 §8.4 自认安全未解决） | 机制层（"安静"目前靠美术与文案，不靠可验收预算） |

**本轮三个新判断：**

1. **Hearth 缺的不是模块，是"可验收的克制"。** 它的注意力承诺目前写在 Must 里（≤1 小卡 / ≤2 chip），但没有对应的判定、预算与负例。DeepSeek 恰好把这一层做成了机制。这是本次最值得抄的一层，且**不涉及任何执行权限**。
2. **炉心应该从 UI 隐喻升级为架构角色。** DeepSeek 的 Router 有明确定义：*"全局的序点（Sequence Point）、协调点和记忆"*。Hearth 的炉心天然占这个位置，但产品合同里没有把它写成职责，导致"谁拥有全部项目的当前状态"这个问题无主。
3. **原文 §5/§8.4 实际上替 Hearth 论证了本地优先。** 它说环境（未提交修改、私有凭据、内网依赖）无法复制，云端接入端侧设备是最大安全隐患。这是"不上云"的正面论据，不是保守退让。

## 1. 先还原论证链，而不是抄模块清单

前几轮文档把文章概括成"五个模块 + 实验数据"，容易读成一份架构选型清单。实际它的推理是一条链：

```text
观察：一个人只能同时跟进 3–5 个活跃 Session
        ↓
诊断：单 Session 设计把「上下文管理」和「项目管理」压在同一个对象上
        ↓
命题：Session 应是实现细节；瓶颈从模型能力转移到人的注意力
        ↓
约束：既要连续（跨信道、跨时间），又要高效（并发、不阻塞）
        ↓
结论：连续性与吞吐量不可兼得 → 分层
        ↓
五个模块（双层架构 / 事件驱动 / 面向人的交互 / 存算分离 / Watchdog）
```

关键在「诊断」这一步：**问题不是"Agent 不够强"，是"Agent 把内部结构暴露给了人"**。这句话对 Hearth 有直接杀伤力——Hearth 的线程、项目、观察器、洞察、分析、运行记录，同样是把内部结构暴露给了用户。炉心叙事是在**修辞层**解决这个问题（你不用管那些，看火就好），但产品合同在**结构层**仍然要求"项目聚焦 / 观察新鲜度 / 权限边界入口"。两者没有对齐。

### 1.1 四个特征 ↔ 五个模块的对应关系（原文自己的映射）

| 特征 | 支撑模块 | 原文的关键手段 |
|---|---|---|
| 连续 | 双层架构 §2 | Router 常驻，跨信道全局记忆 |
| 高效 | 双层架构 §2 + 面向人的交互 §4 | Worker 隔离并发；异步 ReAct Loop |
| 主动 | 事件驱动 §3 | 两级过滤、订阅直通、投机执行 |
| 持久 | 存算分离 §5 + Watchdog §6 | 无状态计算 + 端侧 daemon；外部控制回路 |

**注意第四行的方向**：它把"持久"解成"云端常驻"。Hearth 把"持久"解成"余烬还在"。两条路都能走到"用户回来时东西还在"，但代价结构完全不同——第 5 节展开。

### 1.2 原文自己划的三条边界（比模块更重要）

- **§8.1 长程记忆是硬瓶颈**：*"当运行周期拉长到跨月甚至更长的时间跨度时，长程记忆便成为制约可扩展性的主要瓶颈"*。它承认 Chain of Recall 只解决"近期任务与会话历史的按需检索"。
- **§8.4 安全与隐私未解决**：*"如果没有办法很好的解决安全与隐私问题，那么 Super-agent 只有在一个很小且可信的范围才能工作"*，并点名两个具体风险：云端被攻破则全部端侧设备可被控制；凭据一旦进入上下文就会泄露。
- **§4.1 异步机制"已实现但未默认开启"**：*"这一异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启"*。

## 2. 必须校正的一点：实现状态有三种，不是两种

前几轮（包括我自己的补遗）在"文章 vs 原型"上反复摇摆，根因是把实现状态当成二值。原文 + README 合起来其实是三值：

| 状态 | 例证 | 正确表述 |
|---|---|---|
| **A. 设计主张** | Chain of Recall、存算分离、BYOM、Watchdog 语义判断 | 论文式方向，公开原型未证明 |
| **B. 已实现但默认关闭** | 异步 ReAct Loop（§4.1 明说） | **不能说"未实现"**，也不能说"已启用" |
| **C. 已落地** | 双层架构、订阅直通、两级过滤、Mandate、Ticket/Assignment、Outbox | 可在 `6337fc8` 源码中定位 |

这三分法要写进后续所有引用规则里。尤其 B 这一类，之前没有任何一份文档提到过——它是"厂商已有能力但选择不默认开启"，对 Hearth 的含义是：**同一套机制，激进方也会因为风险而默认关闭**；默认值是设计决策，不是能力证明。

## 3. 灵魂层对接：同一个命题的两种推导

### 3.1 逐句对读

| 原文 | Hearth |
|---|---|
| *"多任务的上限取决于人的注意力"* | "有事它轻敲一下，没事它安静陪着" |
| *"Session 应当是系统的实现细节，而不应是用户的认知负担"* | "你不是打开一个 AI 工作台，你是走近一座私人炉边" |
| *"它只负责人类交互与任务分派，甚至可以不配备 Bash 工具"* | "炉心不会刷屏"；行动必须本线程确认 |
| *"只有在确认问题并找到简单的修复方案后，才会把结果交付给用户，否则全程保持安静"* | "没事就黯一点、静一点" |
| *"单次回复不超过 100 词"* | "≤1 小卡 / ≤2 chip" |
| *"Router 层……全局的序点、协调点和记忆"* | 炉心 = 关系温度 + 在场感 |

前五行是**同一个约束的不同表述**，第六行是 Hearth 有而原文没有的：原文的 Router 是功能性的（序点/协调/记忆），Hearth 的炉心还多一层**关系温度**（旺/温/黯）。这是 Hearth 真正的差异化，不是装饰——后面 6.3 会说明它为什么必须被机制化，否则会变成纯美术。

### 3.2 差异的根源：一个做机制，一个做体验

原文把"少打扰"翻译成可执行判定：谁能产生候选（准入表）、什么强度（explicit/inferred）、什么模式（off/observe/auto）、什么时候算值得说（报告状态 + 24h 门槛）、说多少（100 词）。

Hearth 把"少打扰"翻译成界面约束：≤1 小卡、≤2 chip、不抢焦点、无用户消息不注入（`GET /proactive` 的 `hasUserMessage` 检查就是在实现这条）。

**差别的后果**：Hearth 的约束是**呈现时**生效（已经决定了要说，只是说得少）；DeepSeek 的约束是**决策前**生效（先决定要不要说）。前者防"刷屏"，后者防"想了不该想的"。产品合同第 3 节其实写了后者（"评估是否值得主动打扰"），但**没有任何可验收的判定**，这就是缺口。

### 3.3 结论

Hearth 的灵魂不缺意志，缺**证据**。`NARRATIVE.md` 说"有事轻敲，没事安静陪着"，这句话今天无法被测试证伪——你不知道它是否真的安静，还是只是 UI 一次只显示一张卡。DeepSeek 提供了一套把这句话变成可测命题的模板。**这才是本文要说"可以借鉴"的真正含义：不是借功能，是借可证伪性。**

## 4. 七个机制的逐条深接

每条给四项：Hearth 对应物 → 可迁移不变量 → 最小形状 → 不要照抄什么。

### 4.1 序点 / 全局记忆 ↔ 炉心作为架构角色

**原文**：Router 是*"全局的序点（Sequence Point）、协调点和记忆"*，且*"不直接执行具体任务"*，甚至可以不配 Bash。

**Hearth 现状**：观察走 `ProjectObserver`，规则走 `project-insight`，分析走 `project-analysis`，UI 是 ViewModel 投影。**没有一个实体声称"我知道所有项目的当前状态总和"**。用户跨项目提问时，答案由各子系统拼装；"上一次结论是什么"要靠查询历史。

**可迁移不变量**：存在唯一一个序点，它看到的顺序就是用户看到的顺序；它不做事，只记住并解释。

**最小形状（不改代码，先改合同）**：

```text
炉心（Sequence Point）
  输入：已判定的候选（Insight / 候选卡）+ 已发生的用户决定 + 当前授权快照
  不做：读原始事件流、跑规则、调模型、执行
  输出：唯一一份 NarrativeState（火焰/故事/一条观点）
  不变量：任何呈现给用户的状态都必须经过它；任何模块不得直接改它
```

这条一旦写进合同，会顺带解决一个现存隐患：`observe-view.ts` 在 stale 时仍用旧数据算 `deriveFlame`，本质是"投影层自己做了判断"。序点模型要求**投影只能读序点给的结论**，不能自己重算。

**不要照抄**：不要为此建一个常驻 LLM Session。Hearth 的序点可以是纯确定性代码 + 一次投影，成本为零。原文自己也说 Router *"部分逻辑未必需要调用 LLM"*。

### 4.2 两级过滤 ↔ Hearth 已有的"规则先行"，但缺强度字段

**原文**：*"在调用大模型之前先用确定性策略筛除噪音"*；程序层是 Fast Path，语义层是 Slow Path，且语义层是*"面向人类的自然语言扩展点"*。

**Hearth 现状**：`DiscoveryService` + insight 规则 + suppression 已经是 Fast Path；模型分析是 Slow Path；`GET /proactive` 的 `hasUserMessage` 也算一道快筛。**架构上已经对了。**

**缺的是三样**：

1. **准入强度没有成为数据**。原文区分 `explicit` / `inferred`，并让强度一路传到 Mandate 与重验。Hearth 的候选卡没有"我凭什么提这件事"的强度字段，导致用户无法区分"你说的事我要求你查的"和"你自己想到的"。
2. **语义层不是扩展点**。Hearth 的规则是代码；原文的规则是团队可编辑的提示词文本，且逐条记录 `rule_id` 与匹配理由。
3. **没有"为什么现在"的可审计记录**。候选卡有 `whyNow` 文案，但那是给用户看的叙述，不是给审计看的判定依据。

**最小形状**：候选卡增加三个不可由前端决定的字段——`strength`（explicit/inferred）、`ruleRefs`（命中的规则 ID + 理由）、`wouldPresent`（本来要不要呈现）。**全部只写不执行。**

**不要照抄**：不要引入 Admission table 的二维矩阵（范围 × 成员 × 是否点名）。Hearth 是单用户、单信任域、项目由用户显式登记，"谁能开口"这个问题不存在。照搬会把组织 ACL 复杂度搬进个人工具——这一点第四轮补遗已经警告过（C10），此处再次确认。

### 4.3 订阅直通 ↔ 已立项研究的后续事件

**原文**：订阅直通让*"同一 Thread 下的后续事件由程序直通已订阅的 Worker，无需 Router 层再次调用工具转发"*。实验数字：去掉直通后 Router 决定数 **+30%**，读缓存 token 从 **2323 万 → 3177 万（+37%）**，而任务完成时间**基本不变**。

**这条数据的含义常被读错**：它不是说直通更快，而是说**直通省的是"中枢的判断次数"，不是"任务的速度"**。这是纯粹的成本优化。

**Hearth 对应物**：用户已经批准了一个研究主题（比如"这个项目的测试覆盖率问题"），此后该项目产生的新 JUnit 报告、新提交，现在都要重新走"事件 → 规则 → 候选 → 是否呈现"的全链路。而实际上这些事件**已经归属于一个在办的研究**，不需要中枢再判断一次。

**最小形状**：研究任务（ResearchJob）持有该项目的订阅；订阅期间，匹配的观察事件作为**上下文直送研究任务**，不再产生新的候选卡。**关键不变量与原文一致：直送的是上下文，不通的是授权。** 订阅不得让研究任务获得任何原本没有的范围。

**不要照抄**：不需要为此建线程级多对多订阅表。项目与研究是一对多，一张 `research_job_project` 关联就够。

### 4.4 Inline & Spill / Chain of Recall ↔ 观点八问天然就是引用图

**原文**：核心命题是*"浪费上下文窗口，就是浪费模型的智能"*；做法是对象有唯一 ID、注入时内联下一跳 ID、召回结果再内联下一跳——沿引用图逐跳展开。

**Hearth 对应物被严重低估了**：产品合同第 5 节要求每个观点回答八问，其中"我发现了什么（可定位到来源）""我研究过什么（链接+访问时间）""你决定了什么""后来发生了什么"，**本身就是一张引用图的字段定义**。也就是说，Hearth 不需要先建 Chain of Recall 再谈上下文——它已经要求把引用关系写下来了，只是没把它当检索结构用。

**最小形状（不引入新概念，只加一条约定）**：

```text
每个观点的八问字段在注入模型时，除正文外只内联：
  证据 ID 列表（不内联全文）
  上一版 OpinionRevision 的 ID
  关联 Decision 的 ID
→ 模型需要全文时，通过既有读取接口按 ID 取，返回结果同样附带下一跳 ID
```

这就是"按需展开"。它同时解决一个真问题：Hearth 现在把证据、事件、文档摘录一起塞进分析上下文，`packages/project-analysis/src/context/files.ts` 就是在做硬性裁剪——`MAX_FILE_BYTES` 只读文件前缀、算的是**前缀的 sha256**（注释原文：*"This is the hash of the captured prefix, not an unbounded whole-file hash"*），并返回 `truncated: opened.size > prefix.length`。

也就是说，**Hearth 已经实现了 Spill 的一半**：它知道"这里被截断了"，但没有"续读入口"——模型拿不到那个被截掉的 ID，只能基于前缀判断。原文的 Inline & Spill 正好补上这一半：`truncated: true` 时应同时内联一个可读取全文的引用 ID，让模型自己决定要不要多跳一次。这是一个**接口约定级别的改动，不是新子系统**。

**不要照抄**：不要声称这就解决了上下文压缩问题。原文 §8.1 自己说长程记忆是瓶颈；Hearth 的 Context Runtime R3 Fact-Loss 闸门仍然必须单独过。

### 4.5 批处理 ↔ 候选评估按窗口合并

**原文**：Router 积压时把多条 Trigger 合并进一次调用。实验：到达速率 1→40 条/分钟，batch 1.0→2.8，单次请求耗时 2.5s→3.9s（增长慢于 batch），**单个决定分摊的推理时间 6.4s→1.6s**。

**这条对 Hearth 是纯收益，且直接对应现有痛点**：产品合同要求"每日预算"和"研究频率"，说明成本是要控制的。而现在每个候选事件都独立走一次判定，等于永远在 batch=1 的区间运行。

**最小形状**：候选评估加一个**窗口**（例如 15 分钟，或"下次用户交互前"），窗口内的候选合并成一次判定；单条紧急事件（用户显式发起的检查）不排队。

**不要照抄**：不要把这个当成吞吐优化来宣传。Hearth 的事件量远低于原文的团队群聊负载，省下的算力可以忽略；真正的收益是**减少判定次数 = 减少"想过要不要打扰"的次数**，而那正是注意力成本的来源。

### 4.6 投机执行 ↔ 从"影子记录"升级为"做但不交付"

**原文**：*"Agent 先在后台尝试复现并寻找修复方案，只有在确认问题并找到简单的修复方案后，才会把结果交付给用户，否则全程保持安静。"*

**这是全文与 Hearth 灵魂最契合的一条**，因为它是"安静"的**主动形态**：安静不是不做事，是**做了但没结果就不出声**。

Hearth 现在的影子模式（PR#12 的 S1）只记录"我会做什么"（`would_accept`），不做。DeepSeek 更进一步：**在零外发范围内真的做**。

**Hearth 可安全采用的版本**（严格限制在本地、只读、零外发）：

| 允许"投机"的部分 | 明确不允许 |
|---|---|
| 读已登记项目的 Git 状态、已授权 JUnit 报告 | 读未登记路径、读用户 home 下其他目录 |
| 跑确定性规则、做本地统计与差分 | 调远端模型、发起公网检索 |
| 组装"研究草稿"（问题陈述 + 已有证据 + 缺口） | 生成对外文本、写仓库、执行命令 |

**判定规则**：草稿只有满足"能形成可证伪观点 + 有来源 + 非重复"三条件才浮出；否则**不记录、不呈现、不计入打扰预算**。

这条直接回答了一个 Hearth 尚未回答的问题：**"没事"的时候炉心到底在做什么？** 现在的答案是"没做事"；有了投机研究，答案是"在试着看有没有事，没看成就不吵你"。后者才是"安静陪着"的物理实现。

**不要照抄**：绝对不能借用它的"静默复现并修复"。那需要执行权限，与 Hearth 合同第 4 节的"项目改动/命令/实验一律逐案确认"直接冲突。

### 4.7 信道带宽与 100 词 ↔ 主动卡的字数预算

**原文**：*"我们验证过的一条简单有效的硬性规定是单次回复不超过 100 词"*，并按信道区分：IM 低打扰轻量，GitHub/邮件高信息密度。

**Hearth 对应物**：`≤1 小卡 / ≤2 chip` 是**数量**约束，没有**长度**约束。一张 800 字的卡依然"只有一张"，但对注意力的消耗远超两张 50 字的卡。

**最小形状**：给主动呈现加**字数 + 阅读时长**双预算，并按状态分级（旺/温/黯 不同预算）。**并且做成可测**：超出预算的卡不得进入呈现队列，而不是由作者自觉。

**不要照抄**：不要照搬 100 词这个数字，中文的信息密度不同。但"这个数字必须是硬性且可校验的"这一点必须照搬。

## 5. 反向价值：这篇文章替 Hearth 论证了三件事

前面都是"我们能学什么"，这一节是"它替我们证明了什么"。这对一个还没验收的产品尤其重要。

### 5.1 本地优先不是保守，是与前沿设计的一致结论

原文 §5.2 论证了环境为什么不能上云：*"真实工作环境往往包含未提交的本地修改、私有凭据、内网服务依赖以及特定的硬件或工具链"*，同步*"成本很高，还容易出现信息遗漏"*。于是它的结论是"环境留在原地"。

Hearth 把"环境和状态都留在本地"，比它更彻底。**同一套理由，更彻底的结论。** 也就是说：Hearth 的本地优先不是技术能力不足的妥协，而是把原文的这条推理走完了。

### 5.2 不做全自动执行，有来自最激进一方的依据

原文 §8.4 自己承认：云端 Loop 一旦被注入攻破，*"其连接的全部端侧设备都面临被控制的潜在风险"*，并要求*"让 Agent 能够在完全不接触凭据本身的情况下使用凭据"*——而这个机制它**没有给出实现**。

对比 Hearth 产品合同第 4 节：执行默认禁止、逐案确认、外发前预览。在授权完备性上，**Hearth 比这篇文章更成熟**。这一点应该写进定位文档，避免团队在"对方更先进"的错觉下反向削减自己的红线。

### 5.3 Watchdog 不能有写权，已被多方证据支持

原文 §6 说 Watchdog*"本身也是一个具备完整工具能力的 Agent Session"*，维护者可以让它*"在线修正主系统的行为，例如增删提示词、调整触发规则"*。这是它最危险的设计，而且它自己在 §8.4 没有回应这一条。

Hearth 若做监控，必须遵守第四轮已冻结的 W1/W2 两个隔离条件（证据独立、权限独立）。**本次补充一条更简单的判据**：如果一个监控器能修改它正在监控的规则，那它就不是监控器，是第二个作者。

## 6. 对"灵魂"的三条具体修订建议

这一节是可以直接落到 `NARRATIVE.md` / 产品合同的文字建议，不是新功能。

### 6.1 把"安静"从 UI 约束升级为有预算的机制

现在：`Must: 有事才主动：≤1 小卡 / ≤2 chip`（呈现层约束）

建议补一条并列的 Must：

> **克制须可测**：任何一次主动呈现前，必须能回答三个问题并留下记录——(a) 凭什么现在说（`strength` + 命中的规则 + 时间依据）；(b) 说多少（字数与卡数在预算内）；(c) 上次说到哪（去重与冷却依据）。三者缺一，不得呈现。

理由：这让 S4「有事克制」从美术验收变成行为验收，也让"没事安静陪着"第一次可以被证伪。

### 6.2 把炉心写成序点角色，而不只是视觉隐喻

现在：`炉心 = 和你之间的关系温度；页面明暗、焰势跟着它走`（视觉定义）

建议补一句职责定义：

> **炉心同时是系统的序点**：它是唯一持有"当前所有项目状态总和"的地方。观察、洞察、分析各自产出判断，但只有炉心把它们合成用户看到的唯一状态；任何模块不得绕过它直接改变呈现。

理由：解决"谁拥有全局状态"无主的问题，并为 4.1 的 stale 投影隐患提供合同依据。

### 6.3 明确"对话是默认信道，不是唯一信道"

原文 §8.2 有一句直接挑战 Hearth 的话：*"以聊天窗口为中心的交互在一定程度上是路径依赖的结果"*。

Hearth 的主表面就是对话。这条挑战不能回避，但也不必投降。建议的表述：

> 对话是**注意力成本最低的默认信道**，不是产品的边界。炉心可以出现在项目视图、卡片、通知以外的形态；但任何新信道都必须遵守同一套呈现预算，不得因为"换了个地方"就豁免克制。

理由：既保住 NARRATIVE 的"主路径永远是聊"，又给后续形态留了合法入口，并且把"克制"提升为跨信道的不变量——这恰恰是原文 4.2「多信道交互」的真正教训（按带宽定制，而不是按信道豁免）。

## 7. 可证伪的验证设计（离线、零外发）

承接第四轮的研究纪律：以下都不需要真实模型、不需要外发、不需要真实执行器。

| 编号 | 命题 | 最小实验 | 通过条件 | 失败含义 |
|---|---|---|---|---|
| F1 | 克制可测 | 用合成项目事件回放，统计"候选 → 呈现"漏斗：生成数、被预算拦下数、被去重拦下数、实际呈现数 | 每个被拦下的候选都有可查原因；呈现数与日志计数一致 | 说明"安静"仍只是文案 |
| F2 | 投机有净收益 | 同一批合成事件，对比"直达呈现"与"先投机后呈现"：呈现数、误报数、平均字数 | 呈现数下降、且无高价值候选被漏 | 说明投机只是延迟 |
| F3 | 序点一致性 | 双项目各一条 canary 事件 + 跨项目提问 | 任一视图内不出现另一个项目的标识；同一时刻两个视图的火焰结论一致 | 说明序点职责未成立 |
| F4 | 强度可辨 | 人工评阅随机抽样的候选卡 | 评阅者能区分 explicit 来源与 inferred 来源，且判断与 `strength` 字段一致 | 说明强度字段没有表达出来 |

**共同前提**：全部使用合成数据；不调用 Pi；不产生任何写操作；结果只记录在 `handoff/EVIDENCE/`。

## 8. 明确的拒绝清单

| 拒绝项 | 理由 |

| 云端 Router + 端侧 daemon 的 BYOM 形态 | 与"本地优先"直接冲突；且原文 §8.4 自认该形态安全未解决 |

## 10. 一句话结论

这篇文章真正的贡献不是五个模块，而是**把"少打扰人"从一句态度变成了五个可判定的机制**。
Hearth 的炉心叙事已经说出了同一句话，而且比它多一层关系温度；缺的是让这句话可以被证伪的那层机制。
**所以正确的借鉴姿势不是搬它的架构，而是借它的尺子——量一量我们的"安静"，到底是设计，还是修辞。**

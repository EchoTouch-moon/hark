# M0-C 合成观点与反馈存储

迁移 v3 增加独立的 fixture 项目状态、观点、观点版本、不可执行方案和反馈表，不改写 v1/v2。项目与观点话题、版本与项目、反馈与版本使用外键及唯一约束；观点版本、方案和反馈禁止原地更新或删除。方案的数据库约束要求 `executable` 为 JSON 布尔 `false`。

`src/fixture-opinion-store.ts` 目前只保存 `draft`：版本写入、方案写入及当前版本指针更新在一个事务里，以 `expectedRevision` 检查旧版本；第二版及之后必须记录前版 ID 与修订原因。反馈绑定具体版本，同一项目的幂等键只有在反馈 ID、目标和完整内容一致时才可重放。用户的采纳、修改、搁置或反驳不会删除历史，也不等于事实被证伪。

读取、写入和反馈都先检查当前项目授权与 fixture 项目状态，并在同一事务中重查来源。当前支持合成观察证据及合成用户决定：前者必须匹配 Chronicle 的 source、event、project、epoch、时间及文本；后者必须匹配用户决定的项目、版本、时间、内容及当前状态。决定更新或撤回后，引用旧版本的观点不再可读，但历史保留。撤权、暂停、过期、来源禁用或重置后，原记录保留，但该 API 不再返回失效观点。数据损坏或归属不符也失败关闭。事务内查找能力在回调结束后失效，不能留到撤权之后继续使用。

测试 `tests/fixture-opinion-store.test.ts` 和 `tests/fixture-chronicle.test.ts` 使用虚构数据，覆盖 v1→反馈→v2、原因与重启、两连接顺序模拟旧版本冲突、撤权、跨项目、来源失效、错误内容及数据库约束。完整本地结果见 `handoff/EVIDENCE/m0c-fixture-opinion-check-2026-11-03.txt`；两连接顺序模拟不是并行压力测试。

**未实现**：真实身份认证、统一的正式项目生命周期、真实读取安全边界、真实研究来源和用户决定的可信验证、实际并行竞争测试、生产展示和模型/网络集成。当前 `Feedback` 不单独表达“拒绝”，后续应在版本化合同中明确，不将其自动当作事实证伪。fixture 的 scope 必须来自未来可信服务端上下文，不能直接把客户端传入的 principal 当成认证。此模块不能证明观点真实或有用，也不能作为真实项目读取的安全 Gate。
